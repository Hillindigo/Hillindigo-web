这个网站是怎样设计的

Hillindigo 主要用来记录生活。平时拍下的照片、旅行中的见闻、偶然冒出的想法，都可以放在这里。学习技术时整理的笔记，也会一起留下来。

设计这个网站时，我希望它有自己的样子，也希望写东西、发照片这件事足够方便。页面可以慢慢调整，内容也可以一点点积累，不需要一开始就把每个栏目填满。

一、先划分职责，再选择页面形式

网站目前分为首页、随笔、记录、生活和关于五个部分。

它们不是五个装不同内容的容器，而是承担不同的阅读任务：

  • 首页建立第一印象，并引导访客找到内容。
  • 随笔承接短想法，不要求每次记录都写成完整文章。
  • 记录整理技术学习、实践过程和资源。
  • 生活保留影像与日常，让网站不只是一份技术清单。
  • 关于集中提供个人介绍、简历和联系方式。

这种划分的出发点，是让不同成熟度、不同长度的内容都有合适的位置。短笔记不必为了发布而扩写，技术文章也不应该被埋在日常动态里。

不过，栏目清晰不等于入口有效。对于从简历进入的访客，更重要的是快速找到代表作品。这也是当前首页还需要继续完善的部分：在保留视觉表达的同时，直接展示精选文章和项目，而不是让读者自己探索所有栏目。

二、公开阅读与后台编辑，采用不同的实现方式

博客的公开页面以阅读为主，内容更新频率远低于访问频率。因此，公开站使用 Astro，在构建阶段生成静态页面。

这是一项针对场景的取舍：读者打开文章时，不需要先启动完整的后台应用，也不需要为了获取正文而进入登录或数据库查询流程。

与此同时，内容编辑有另一组需求：保存草稿、上传媒体、查看预览，以及确认发布。这些操作需要状态管理和明确的反馈，不适合直接放进公开页面。

因此，项目将公开展示与后台编辑分开：

  • 公开站负责内容呈现和阅读交互。
  • 后台负责编辑、媒体管理和发布操作。
  • 共享的内容模型负责定义双方使用的数据结构与规则。

这样做并不是为了增加架构层次，而是因为“读文章”和“管理文章”的职责不同。公开页面可以保持相对简单，后台也能独立演进，不必把编辑功能和管理权限带给普通访客。

三、把页面内容与视觉布局分开

如果首页介绍、导航入口、个人资料都写在页面组件里，每次修改一句话，都需要进入源码寻找对应位置。

Hillindigo 将首页信息和关于页资料放进内容配置，页面读取配置后负责渲染。例如，首页标题、简介和按钮去向属于内容；环形导航的位置、配色和运动方式属于展示逻辑。

两者的边界是：

内容配置决定“展示什么”，页面组件决定“怎样展示”。

这也避免了另一个极端：为了让所有东西都能在后台修改，把整个页面变成一个复杂的低代码编辑器。

对于个人博客，频繁变化的是文章与资料，而不是每天重新设计页面结构。因此，优先配置化高频变更内容，比开放所有布局参数更适合当前规模。

文章与媒体则保存在内容目录中，配合 Git 留下变更记录。这样的组织方式适合以文本为主、由个人维护的网站；代价是内容更新需要经过同步和构建，不适合直接照搬到高频多人协作的业务系统。

四、发布流程中，最重要的是区分三个动作

后台编辑最容易产生歧义的地方，是把“保存”“预览”和“发布”混在一起。

它们实际上对应三种不同的意图：

  1. 保存草稿：保留当前修改，不改变公开内容。
  2. 更新预览：查看内容经过真实构建后的效果。
  3. 正式发布：确认将选定内容交给公开访客。

Hillindigo 的内容流程围绕这三个动作展开：

编辑内容 → 保存到草稿 → 更新 Preview → 确认选定内容 → 正式构建与发布

项目使用不同分支区分日常开发、内容草稿和正式状态。开发分支用于功能修改与验证；草稿分支保存待预览的内容；正式分支作为公开发布的来源。

这里真正需要解决的问题，不是“怎样把文件推送出去”，而是：

当多篇文章同时处于不同完成阶段时，发布其中一篇，不应该顺带公开其他草稿。

因此，正式发布的边界应落在选定文章及其必要资源上，而不是简单地把整个草稿状态覆盖到正式站。

图片等媒体也属于这条链路的一部分。只发布正文却遗漏引用文件，会得到一篇文字完整、图片失效的文章；反过来，不加区分地同步全部媒体，又可能把尚未准备公开的资源带出去。

这使得发布不再只是一个按钮，而是一项需要检查内容范围和依赖关系的操作。

五、共享内容模型，减少前后台规则不一致

公开站和后台都要理解文章数据。如果双方各自维护一份字段定义，就可能出现后台允许保存、前台却无法正确展示的情况。

因此，项目将内容模型放在共享模块中，用于统一字段、类型与相关规则。

以封面为例，看起来只是给文章增加一张图，实际却需要回答：

  • 老文章没有封面时是否仍能显示？
  • 封面为空时采用什么展示方式？
  • 后台上传后的地址，公开站能否访问？
  • 预览与正式发布是否使用相同规则？

类似问题说明，新增一个字段并不等于完成一个功能。只有编辑、保存、预览和公开阅读对它有一致的理解，这项功能才形成了完整链路。

共享模型不能消除所有错误，但能减少同一个规则在不同位置被重复解释的机会。

六、视觉风格服务于阅读，而不是替代内容

网站采用青绿色和米白色作为主要色彩，中文衬线标题建立识别度，正文与导航则使用更适合连续阅读的无衬线字体。

首页的视频背景、环形轨道和猫头像，表达的是个人气质；进入文章后，视觉重点应转向标题层级、段落、代码和表格。

两种页面不必拥有同样强度的装饰：

  • 首页可以更有表现力。
  • 列表需要方便比较标题和摘要。
  • 正文需要减少干扰，支持长时间阅读。

响应式设计也不能只把桌面页面等比缩小。手机屏幕上，标题、按钮和装饰之间的空间竞争更明显，因此需要重新调整排列和尺寸，并使用可展开的导航。

首页还设置了静态海报作为视频的替代画面，并为减少动态效果的偏好提供样式处理。这些设计有助于保留基本阅读体验，但是否真正流畅，仍需要结合设备和网络条件验证，不能仅凭页面能打开就下结论。

七、如何判断一次改动真的完成了

这类网站的验证至少有三个层次。

第一层是代码和构建。
检查类型、内容结构和构建结果，确认页面能够生成。

第二层是实际交互。
确认导航能打开、链接去向正确、文章可读，手机上的代码与表格不会破坏整页布局。

第三层是发布边界。
确认草稿没有意外公开，正式文章引用的资源齐全，预览状态与正式状态没有混淆。

这三个层次不能互相替代。构建成功不代表手机上好用，预览正常也不代表选定内容已经正确发布。

对于个人博客，测试规模可以适度，但验证对象需要明确。比起只记录“检查通过”，更有意义的是说明检查了哪条路径，以及哪些部分仍未验证。

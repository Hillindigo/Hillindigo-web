【Agent 原理】Session：Agent 的核心运行时容器

在以 Codex 为代表的 coding agent 系统里，真正让 Agent 能连续工作、调用工具、记住上下文、处理用户输入、响应中断、维护状态的，是一套运行时机制，Session 就是这套机制的核心之一。

一句话理解：Session 是一个 Agent Thread 的运行时上下文，承载了一次对话线程从初始化、接收输入、执行 turn、调用工具、更新状态，到最终关闭的完整生命周期。

它不是我们常说的 web session，也不是 HTTP session。它更像一个正在运行的 Agent 实例，内部包含配置、历史、工具服务、事件通道、当前任务，以及 Agent 当前状态。

一、Session 解决什么问题

Agent 要稳定运行，至少要解决五个问题：

第一，Agent 需要知道自己是谁。 每个 Session 绑定一个 conversation_id（当前 thread 的 ID）。多 agent 场景下，一个 root thread 可派生出多个 sub-agent，各自有 thread，但共享同一个更高层的 session_id。

第二，Agent 需要保存上下文。 模型每一轮输出都依赖历史、配置、工具结果、用户输入和系统状态。SessionState 保存这些会话级可变状态：上下文历史、配置、token 用量、rate limit、上一轮 turn 设置等。

第三，Agent 需要调用工具。 coding agent 不止生成文本，还要执行 shell、读写文件、调 MCP server、处理 approval、用 plugins 和 skills。SessionServices 持有这些运行时服务：model client、MCP connection manager、exec manager、hooks、plugin manager、skills manager、AgentControl 等。

第四，Agent 需要被驱动。 外部输入不直接调模型，而是先包装成 Op（UserInput、Interrupt、Shutdown、InterAgentCommunication），进入 submission_loop，由 loop 分发给不同 handler 处理。

第五，Agent 需要对外发事件。 执行过程中持续发出事件：session configured、turn started、tool call、agent message、turn completed、error 等。TUI、app-server、exec 模式都靠这些事件更新 UI 或输出结果。

二、Session 的核心结构

完整定义（Rust，截取自 Codex 源码）：

pub(crate) struct Session {
    pub(crate) conversation_id: ThreadId,
    pub(crate) installation_id: String,
    pub(super) tx_event: Sender<Event>,
    pub(super) agent_status: watch::Sender<AgentStatus>,
    pub(super) out_of_band_elicitation_paused: watch::Sender<bool>,
    pub(super) state: Mutex<SessionState>,
    /// Serializes rebuild/apply cycles for the running proxy; each cycle
    /// rebuilds from the current SessionState while holding this lock.
    pub(super) managed_network_proxy_refresh_lock: Semaphore,
    /// The set of enabled features should be invariant for the lifetime of the
    /// session.
    pub(super) features: ManagedFeatures,
    pub(super) pending_mcp_server_refresh_config: Mutex<Option<McpServerRefreshConfig>>,
    pub(crate) conversation: Arc<RealtimeConversationManager>,
    pub(crate) active_turn: Mutex<Option<ActiveTurn>>,
    pub(crate) input_queue: InputQueue,
    pub(crate) goal_runtime: GoalRuntimeState,
    pub(crate) guardian_review_session: GuardianReviewSessionManager,
    pub(crate) services: SessionServices,
    pub(super) next_internal_sub_id: AtomicU64,
}

最关键的三块：

  • SessionState：保存“状态” —— 会话级可变状态容器：上下文历史、配置快照、token/rate limit、上一轮 turn 设置、auto compact 状态等。
  • SessionServices：保存“能力” —— 集中执行所需服务：模型客户端、MCP、shell 执行、插件、技能、hooks、AgentControl、thread store 等。
  • submission_loop：保存“驱动逻辑” —— Session 创建后启动的后台 loop，不断接收 Op 并分发处理，是 Session 的执行心跳。

三、Session 的生命周期（五步）

  1. 创建 Session：外层 Codex::spawn() 准备配置、模型信息、历史、工具管理器，然后调用 Session::new()。
  2. 初始化运行时：Session::new() 初始化 thread 持久化、上下文历史、MCP、hooks、model client、权限策略、网络代理、插件和技能等运行环境。
  3. 发出 SessionConfigured 事件：通知 UI/客户端当前 thread 已就绪（model、cwd、approval policy、permission profile、初始历史等）。
  4. 启动 submission_loop：此后所有输入都变成 Op 进入这个 loop。
  5. 处理输入并持续发事件：开始一个 turn —— 调模型、执行工具、更新历史、处理 approval、维护 active turn，进度通过事件流发出。

四、Agent 状态：从事件流推导，而非手写字段

Agent 状态不是写死的影子数据，而是从事件流推导出来的：

事件 推导出的状态
TurnStarted Running
TurnComplete Completed
TurnAborted Interrupted / Errored
Error Errored
ShutdownComplete Shutdown

实现上，Session 内部有 watch::Sender<AgentStatus>：每次发事件时先检查能否推导出新状态，能则更新 watch channel。AgentControl、wait_agent 等模块订阅这个 channel，实时感知状态变化。

这是很漂亮的设计：状态不独立维护，而是从事实事件中派生 —— 单一事实来源，天然一致。

五、Session 与多 Agent 的关系

多 agent 场景下，每个 sub-agent 本质上也是独立的 thread，有自己的 Session。但这些 Session 不孤立，共享同一个 AgentControl。分工如下：

组件 职责
Session 负责某一个具体 agent/thread 的运行
AgentControl 负责一组 agent 之间的控制与通信（维护 agent 树、spawn 子 agent、发送 inter-agent communication、查询/订阅其他 agent 状态）
AgentRegistry 记录当前 agent 树、agent path、nickname、role 等 metadata
ThreadManager 负责 thread 的创建、查找、恢复和生命周期管理

一句话：Session 是单个 agent 的运行时核心，AgentControl 是多 agent 协作的控制面。

六、一条简化的数据流

用户 / UI / AppServer
        |
        v
Codex.submit(Op)
        |
        v
submission_loop
        |
        v
Session handler
        |
        v
模型 / 工具 / MCP / Shell / Plugins
        |
        v
Session.send_event(...)
        |
        v
TUI / exec output / app-server client

输入通过 Op 进入 Session，执行过程通过 Event 输出。 Session 站在输入和输出之间，把一次 agent 行为完整组织起来。

七、为什么 Session 是 Agent 的核心之一

Agent 的能力不只来自模型 —— 模型只是推理和生成的部分。真正让 Agent 成为“可执行系统”的，是 Session 这样的运行时容器，它把以下能力组合在一起：

  • 上下文管理
  • 配置与权限管理
  • 工具调用
  • 模型请求
  • 事件流输出
  • turn 生命周期
  • agent 状态维护
  • 中断与关闭
  • 多 agent 通信入口
  • 持久化与恢复

没有 Session，Agent 就只是一组零散函数；有了 Session，Agent 才成为可以被启动、输入、观察、协作和终止的运行实体。

如果说模型是 Agent 的大脑，那么 Session 更像是 Agent 的身体和神经系统：它连接输入、记忆、工具、动作和反馈，让 Agent 从“能生成文本”变成“能持续完成任务”。
